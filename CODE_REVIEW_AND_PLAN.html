01The verdict

Gemini was right about the opportunity and wrong about the engineering. The failure was not cosmetic. The flagship tool does not perform the one operation it exists to perform.

The plan described the audience problem correctly, and the instinct to own the tool instead of sending viewers to an ad-heavy third-party site is sound. But the delivered code never resizes an image to the required pixel dimensions — it has no width or height input at all. It has one input: a maximum file size in KB. Everything the tool claims follows from a value it was never given.

That is why the result looked broken. It was not a polish problem. The requirements were written down as prose in a planning document and then never converted into code that enforces them.

Concretely, feeding a real 4032×3024 phone photo to the shipped resizer, with a UPSC requirement of 500×500 px at 20–300 KB, produced a 3539×2654 file. The tool then printed “Success!”. Four out of four government specifications tested produced wrong dimensions, and the tool reported success every time.

Your instinct about algorithms was correct, and it is worth naming precisely. A button labelled “Enhance” is a claim about a method. This build had no method. There was no background-removal model, no adaptive thresholding, no PDF library, no threat-list lookup — only a file-size loop and some string templates. The claim and the implementation had drifted apart, and nothing in the process could detect that, because there were no tests.

04Three root causes

The individual bugs matter less than the pattern that produced them. There are three, and they compound. Fix these and the next tool behaves differently.

R1 — Requirements were written as prose, then never enforced

The kickstart says “SSC (4×2cm, 10–20KB)”. That is a specification, but it lived in a paragraph. In the code, it became a single number in a form field that the user has to type, and the algorithm never saw the rest. Requirements are data. They belong in a data structure the code reads, with a source and a verification date attached.

R2 — The algorithm optimised the wrong variable

The compressor treats dimensions as free and file size as an upper bound. Both are wrong for this problem. In a government upload, dimensions are a hard constraint and file size is a window. Because the loop sacrifices resolution first and quality second, it produces files that are simultaneously too small in pixels and too small in kilobytes — and it cannot detect that, because it was never told the target.

R3 — “Success” was a UI event, not a verified outcome

This is the most important one. The success message fires when the download is triggered, not when the file is confirmed to meet the requirement. The user's demand — “it must work 100%” — is achievable, but only if it is expressed as an engineering rule:

The rule to adopt For supported inputs, either produce a file that passes the stated checks, or explain clearly why it cannot be done. Never display success for a result that has not been verified against the requirement. The download button appears only after the check passes.

That single rule eliminates the entire P0 class of defects, and it is testable. It is what makes “works 100%” a claim you can defend in a video instead of a hope.

Fix 1 — Make the requirement data, not a form field

Before — the requirement exists only as prose, and the code asks the user to guess 
<div class="form-group">

After — the requirement is a record, and it carries its own provenance AND its own evidence 
{
  id: 'ssc-signature',
  label: 'SSC — Signature',
  width: 140, height: 60,       // read from the official PDF, NOT derived from a cm figure
  minKB: 10, maxKB: 20,         // BOTH bounds. This is a window, not a ceiling.
  format: 'image/jpeg',
  status: 'VERIFIED',
  source: 'SSC "Guidelines for scanning and Upload of Documents" (official PDF, 4 pages)',
  verifiedOn: '2026-09-14',

  // The evidence behind the claim below. Without this the feasibility is an assertion.
  measuredOver: { fixture: 'scan', grain: [0,4,8,12,16,24,32], density: [1,2,4,6] },
  measuredOn: '2026-09-14',
  measuredWith: 'Chrome 152, _verify/browser_truth.mjs',

  feasibility: 'marginal',      // MEASURED: only 7 of 28 realistic inputs reach 10 KB
  preferLarger: 'ssc-signature-large',
  riskNote: 'A dense signature reaches ~13.4 KB and passes; a compact one reaches ~8.8 KB and fails.',
  rules: ['Sign on plain white paper with a BLACK ink pen.', 'NOT in capital letters.'],
}

Two things happen as a result. The code can enforce the requirement, and the interface can be honest about what has actually been confirmed. That second part is what lets you look a viewer in the eye. The measuredOver line is the part most people leave out, and it is the part that keeps the entry honest: the build refuses to ship a feasibility claim that has no sweep behind it.

Fix 2 — Fix the dimensions first; search quality second

Before — dimensions are sacrificed to hit a size ceiling 
// Step 1: guarantee fit at min quality by downscaling dimensions
let minBlob = await getBlob(currentCanvas, 0.05);
while (minBlob && minBlob.size > targetBytes) {          // no iteration cap
  const scale = Math.max(0.1, Math.sqrt(targetBytes / minBlob.size) * 0.92);
  const newWidth  = Math.max(1, Math.floor(currentWidth  * scale));
  const newHeight = Math.max(1, Math.floor(currentHeight * scale));
  // ... the required pixel dimensions are destroyed here, permanently
}
// Step 2: binary search for best quality
let low = 0.05, high = 0.98, bestBlob = minBlob;
for (let i = 0; i < 8; i++) { /* ... */ }
return bestBlob;   // never checked against a minimum, never checked for dimensions
After — dimensions are fixed, only quality moves, and the search is bounded 
const canvas = renderAtExactDimensions(source, crop, spec.width, spec.height);

let lo = 0.05, hi = 1.0, bestBytes = null, bestQuality = null;
const atMax = await measure(1.0);                 // 1 encode
if (atMax <= maxBytes) { bestBytes = atMax; bestQuality = 1.0; }
else {
  for (let i = 0; i < 12; i++) {                  // hard cap: cannot hang
    const mid = (lo + hi) / 2;
    const bytes = await measure(mid);
    if (bytes <= maxBytes) { bestBytes = bytes; bestQuality = mid; lo = mid; }
    else { hi = mid; }
  }
}
if (bestBytes === null)          return { ok: false, reason: 'CANNOT_REACH_MAX' };
if (bestBytes < minBytes)        return { ok: false, reason: 'BELOW_MINIMUM', bytes: bestBytes };
return { ok: true, bytes: bestBytes, quality: bestQuality };
This also fixes the performance problem for free The old loop encoded the full 12-megapixel canvas nine times. Because dimensions are now fixed first, every encode operates on a 500×500 canvas instead — orders of magnitude less work. A correctness fix that also removes the need for a Web Worker is the best kind of fix.

Fix 3 — Verify the artifact before claiming anything

Before — success is announced from the size alone 
const sizeKB = (finalBlob.size / 1024).toFixed(2);
// ... trigger download ...
showAlert(resizerAlert, 'success', `Success! Image compressed to ${sizeKB} KB.`);
// Dimensions never re-read. Requirement never consulted. "Success" is unconditional.
After — the claim is gated on a re-check of the finished file 
const check = verify(spec, {
  width: canvas.width, height: canvas.height,
  bytes: blob.size,    mime: blob.type,
});

if (!check.pass) {
  showStatus('bad', 'Produced, but it failed its own check', check.problems.join('; '));
  return;                       // no download offered
}

showStatus('ok', 'Matches these file requirements',
  `${canvas.width}x${canvas.height} px, ${(blob.size / 1024).toFixed(2)} KB, ` +
  `within the ${spec.minKB}-${spec.maxKB} KB window. Still confirm on the official upload page.`);

Note the wording. “Matches these file requirements” — not “guaranteed government approval”. A file-preparation tool can verify numbers. It cannot verify that a portal will accept a file, and pretending otherwise is the kind of overclaim that destroys an audience's trust the first time it is wrong.

Fix 4 — An honest security tool, or no security tool

The link verifier is the clearest example of a claim outrunning its method. A substring check against seven bank names cannot decide whether a link is malicious. Shortened links are not inherently malicious either — which is exactly why the useful output is disclosure, not a verdict.

Before — a rule that produces both misses and false alarms, presented as a verdict 
const targets = ['sbi','hdfc','icici','axis','pnb','epfo','incometax'];
let typo = false;
targets.forEach(t => {
  if (hostname.includes(t) && !hostname.endsWith('.gov.in')
                           && !hostname.endsWith('.co.in')
                           && !hostname.endsWith('.com')) typo = true;
});
if (typo || hostname.split('.').length > 4) { /* "may be a lookalike phishing domain" */ }
After — show the user the fact they cannot see, and be explicit about the limit 
const KNOWN_SHORTENERS = new Set(['bit.ly','tinyurl.com','is.gd','t.co','rb.gy','forms.gle','wa.me']);
const TRUSTED_GOV = /\.(gov\.in|nic\.in)$/;

// The real defence is comparison: the address the link DISPLAYS vs the address it GOES to.
if (KNOWN_SHORTENERS.has(hostname)) {
  report.warn(`This is a shortened link. Its destination is hidden until you open it. ` +
              `A government department does not send challan or refund links through ` +
              `shorteners. Open the portal yourself by typing the address.`);
} else if (TRUSTED_GOV.test(hostname)) {
  report.ok(`This is an official government domain (${hostname}).`);
} else {
  report.info(`This link goes to ${hostname}, which is NOT an official government domain. ` +
              `Compare it, character by character, with the address printed in the ` +
              `official notification.`);
}
// Stated limit, shown in the interface:
// "This checks the shape of the address. It cannot tell you whether a page is malicious.
//  Only a maintained threat list can do that."
The design principle When a tool cannot establish something, it must say so rather than guess. Telling a frightened user that a genuine bank domain “may be a phishing site” is a real harm. So is passing a shortened link as clean. Honest disclosure of the destination is both more useful and defensible.

06One site, one page per job

Decision: one domain, one page per tool, shared code behind them.

Not one super app. Not many separate websites. The reasoning:

Why not one super app

  • A viewer arriving from a video about signature sizes should land on the signature tool, not a dashboard they must navigate.
  • Every added module multiplies the surface that must be tested. Four half-tested tools are worse than one proven tool.
  • One large bundle loads slower on the rural 4G connection that most of your audience is on.

Why not many separate websites

  • Each site means its own domain, certificate, deployment and analytics — recurring work that produces nothing for the viewer.
  • Brand authority compounds on one domain. Scattered across five, it does not.
  • Shared code (the size-search algorithm, the spec registry, the styling) would be duplicated or lost.

So: one site. Each video links to the exact page for its problem. A small home page lists what exists, but nobody is forced through it. Pages share a stylesheet and the same verified core. 

dhanwala-tools/                    (one domain)
  index.html                       short list of tools; not a dashboard
  tools/
    signature-fit/                 <- the video about signature sizes links here
    photo-fit/                     <- the video about photo sizes links here
    photo-to-pdf/                  <- added when a video needs it
  shared/
    core.js                        size search, crop geometry, verification

Deep links matter more than the home page The address in a video description must open the right tool directly, with the right preset already selected — for example /tools/signature-fit/?preset=ssc-signature. This is a small feature and it is the difference between a viewer using your tool and a viewer bouncing. It was absent from the previous build entirely.

07Who builds what

You asked who writes the code, and whether you need a different developer or a different AI for each tool. You do not. The split that works is by decision, not by task:

You
Choose which problem each video solves. That is the only input that cannot be automated — it comes from your audience's comments and your own experience of the portals.
You
Confirm each requirement against the live official portal, once, per requirement, and record the date. This is the one step that cannot be delegated to a model, because a model cannot log in and see the upload screen. It takes a few minutes and it is what makes the tool trustworthy.
You
Use the finished tool yourself on your own phone before publishing, and check that it feels right. Then decide whether to publish.
I do
Turn the problem into a written requirement, choose the method, write the code, write the tests, run them, and show you the evidence. For every tool, not a different one per tool.
I do
Tell you plainly when something cannot be done reliably — a background-removal model that runs on a low-end phone, for instance, or a live webcam capture that no file can substitute for. A “no” here is worth more than a demo that breaks on stage.
Optional
A second pair of eyes on the requirement check. If you have a friend or a viewer who can confirm a portal's numbers independently, that is genuinely useful. It is not required.
What you should not do Do not write a longer kickstart prompt. The previous build did not fail for lack of detail — it failed because the detail was prose that no code enforced and no test checked. More prose would produce the same outcome. One narrow, verified requirement at a time is the fix.

The fields that matter most are the last three. What is still unknown is more useful than what is known, because it tells you exactly what to test next. Note that the corrected record has one field the original did not: the measurement, and the sweep it was taken over. That is the field that stops the entry from quietly becoming a lie.

The trap was real, and the answer was neither of the two options I offered Your SSC notes said the signature must be 4.0 cm × 2.0 cm — a physical measurement, not a pixel one. At the time I wrote that either the portal validates a pixel box, or it validates printed size and file size only. The document says something more awkward than either: it states a pixel box, and it enforces size and format, and the stated pixel box cannot reliably hold the stated size window. The lesson is not “research more”. It is that a requirement record is not finished until it has been measured, because the contradiction between two stated numbers is invisible until something tries to satisfy both at once.

One more defect, and the re-run is what found it

The suites passed. Then they were run again, with nothing changed, and two of them died — not with a failed assertion but with an error thrown from inside fs:

Error: [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] count 343, threshold 50, scope "turn" target: _verify/fixtures

The harness was deleting its own scratch state: browser_truth.mjs wiped the fixture folder at the top of every run, and test_mutation.mjs wiped its own. That is a normal thing for a test harness to do, and this machine refuses it — it guards against bulk deletion, and it counts deletions cumulatively for the session, so a run that had already removed a few hundred temporary files could not remove forty more.

Note what that failure is not. The tool was not wrong. The registry was not wrong. The measurement was not wrong. The evidence-gathering was destructive, and the budget for destruction ran out. The fix is the right one whether or not a guard exists: a test harness should be idempotent and non-destructive. Fixtures are now written in place, overwriting whatever is there, and the only files ever removed are ones a previous run recorded in a manifest and this run does not want. When the registry has not changed — the normal case — that is zero deletions, permanently. Leftovers are inert: nothing requests a fixture that is not in a job list.

The same lesson as section 05, applied to the tests instead of the tool A harness that can only pass by destroying something is a harness that will one day not run at all. One green run is not proof that a suite is stable; the second one is.

Three more ways the harness itself could fail

Fixing the flakiness turned out to be the largest single piece of work in this section, because a suite that fails on correct code is worse than one that passes on broken code — it teaches you to ignore the result. Three separate bugs, all in the waiting, all found by re-running rather than by reading:

  1. A fixed sleep read the status mid-fit and captured “Fitting... Measuring candidate qualities.” — the app's own in-progress message — and treated it as the verdict.
  2. A stale verdict could be returned. waitForSelector('#report:not([hidden]), #status.bad') matches instantly if an earlier step already left the status on bad, so an assertion could be reading the previous click's result.
  3. Comparing the status text before and after a click is not reliable either. Two consecutive fits can legitimately produce identical text — same preset, same document — so “has it changed?” never becomes true. Sampling the baseline after the click is worse still: it compares the new verdict against itself, and the wait can never end.

The fix is not a longer timeout. It is a write counter: a MutationObserver installed at document-start counts every write to the status element, so “the fit finished” is detected as a new write, followed by a terminal state, regardless of what the text says. The click happens inside the helper, so the baseline can never be sampled at the wrong moment.

phase 1 — showStatus() has been called at least once since the click phase 2 — the status is terminal: kind is 'ok' or 'bad'

File loads were the same bug in a different coat. Detecting completion by “the file-info text changed” fails when two steps load the same fixture — which is exactly what steps 6 and 7 do. They now match on the file name and a width×height pair, which cannot be satisfied by the wrong file and cannot hang on the right one.

Two smaller gaps fell out of the same sweep. This suite printed the captured console errors and never asserted on them — the same “printed is not asserted” gap found earlier in the responsive sweep — so a clean console is now an assertion, and it still passes after deliberately feeding the app files it cannot decode. And the fixture writer no longer deletes anything at all, ever: overwrite in place. Leftovers from an earlier sweep are inert, and every count quoted in this report comes from the intended set rather than from a directory scan, so a leftover can never inflate a claim.

Why this is the same mistake as the original bug The old build announced success without checking the artefact. My model announced a passing size without running the encoder that produces it. Both are a claim standing in for a measurement. The distance between them is only the size of the error — and at a boundary, an error of any size flips the answer.

The two middle cases are the point. Only measurement finds them. That is why the browser is the authority and the static guard is not.

Two flaws I found in my own verification

Worth recording, because both are the same class of mistake as the one being reviewed.

The smaller one: an unrealistic fixture. My first synthetic “photograph” was a smooth gradient with fine noise. When it was reduced from 4032 × 3024 to 200 × 230, the box filter averaged the noise away and left a near-flat image that compressed to a few KB — so the fixture refused requirements that a real photograph would pass. Real photographs keep detail when reduced, because a scene carries structure at every scale and sharp edges stay sharp. The fixture now models that: a face with eyes, brows and a mouth, a collar, plus texture at scales that survive reduction.

The larger one: a fixture that answered only half the question. The signature sweep originally varied scan noise and nothing else. Across seven noise levels the 140 × 60 box never reached 10 KB, so the first honest reading was “unreachable” — and I nearly shipped that. It was wrong. Noise is only one axis of real variation; ink density is the other, and it is the one that decides the answer. An elaborate signature reaches 13.4 KB and passes. One axis would have produced a confident, wrong verdict on the single most important preset in the tool.

There is also a shared fixtures.mjs now, because the suites previously seeded their generators at module scope — so adding a preset changed the images and changed the numbers. Evidence that is not reproducible is not evidence.

Defects I found in my own drafts, and fixed

Worth recording, because it shows the process working. Every one of these was caught by a test, not by reading:

  • A CSS bug that silently broke the hidden attribute. The custom-fields block is a <fieldset> with class="grid4". Because .grid4 { display: grid } outranks the browser's built-in [hidden] { display: none }, setting hidden did nothing and the custom inputs showed on every preset. Fixed with an explicit [hidden] { display: none !important }. A classic, and exactly the class of bug that only a test catches.
  • A residual stretch from rounding the crop to whole pixels. Rounding the crop rectangle to integers reintroduced a 0.02% aspect error when resampling. The crop is now kept as exact floats and rounded only for display.
  • A stale result banner. Changing the requirement left the previous “matches these requirements” message on screen next to a different spec. Changing the spec now clears the result.
  • A scroll trap on phones. I had put touch-action: none on the whole image area, so any finger landing on the photo stopped the page scrolling. Only the draggable frame opts out of native gestures now.
  • Touch targets below the recommended minimum. Buttons rendered at 38 px; Apple recommends 44 pt and Google 48 dp. Raised to 44 px on coarse pointers and narrow screens. This one then turned out to be half fixed: the value was printed by the sweep but never asserted, and the sweep ran a fine pointer, so the coarse-pointer rule was never exercised at all — while this report claimed it was. There is now a separate coarse-pointer sweep with a 44 px floor, an assertion that the context really is coarse, and a negative control that proves the check can fail. See section 09.
  • Unreproducible evidence. The suites seeded their image generators at module scope, so adding a preset changed the order of calls, changed the images, and changed every number. There is now one fixtures.mjs that reseeds explicitly per spec.
  • An unrealistic test photograph. My synthetic photo was a gradient plus noise; reducing it to 200 × 230 averaged the noise away and left a near-flat image, so the fixture refused requirements a real photo would pass. It now models structure at multiple scales, including sharp facial features, because sharp edges are what survive reduction.
  • A misnamed field that would have become a lie. The registry flagged tight boxes with a field called cleanScanRisk, meaning “a very clean scan falls under the minimum”. Measurement showed the real driver is ink density, not scan cleanliness. The field is now riskNote, and the guard refuses a marginal entry that does not say which inputs actually fail.
  • A field that hid the evidence. Each entry declared a single fixture. One image cannot separate “marginal” from “comfortable”, because input variation is the entire question. It is now measuredOver — a declared grid of scan noise and ink density — and the guard refuses an entry whose feasibility has no sweep behind it.
  • Two suites that could not fail. test_old_algorithm.mjs and test_verifier.mjs printed observations and always exited 0, so the runner reported PASS no matter what they found. Both now assert, and their assertions are deliberately inverted: they fail if the old defects ever stop reproducing, because that would mean the reproduction had drifted and the evidence in this report is stale.
  • A test that was measuring the wrong thing. The old-encode-cost check counted encodes and claimed the old algorithm did more work. It does not — it does exactly 10, fewer than the corrected search's worst case. The cost is in the pixels: a 25.9-megapixel canvas encoded ten times. Corrected to measure what actually matters, the finding became 51× instead of a wrong claim about a count.
  • A helper named process, which shadowed Node's global. Calling process.exit() then threw TypeError: process.exit is not a function, so the suite crashed instead of reporting. It happened to exit non-zero, which looked like a normal failure — the worst kind of bug, because it is invisible in a green run.
  • Three bugs in my own test harness — I waited for a download before clicking the download button; my first “impossible window” case was actually possible (1600 × 1200 at 400–450 KB is easily achieved); and my first verdict logic for the IBPS readings sampled a single quality instead of searching. A test that cannot fail proves nothing.

What to say in the video, and what not to

The strongest true thing you can tell your audience “The SSC signature requirement is 140 × 60 pixels and 10–20 KB. It also gives the video a reason to exist beyond “download my tool”.
Do not say the pixel box is “just guidance” I said that earlier in this project and it was wrong. The portal checks size and format; the box determines whether the window is reachable. Those are different claims and only the second one is useful to a candidate.

What is still unverified, and how to close it

Four things remain open, and each one is a twenty-minute job on the live portal:

  1. Does the SSC upload screen actually reject a 140 × 60 signature at 9 KB, or does it accept it? The document says it should reject. Confirming this turns the headline finding from documented into observed.
  2. Does the upload editor force the crop to 140 × 60, or accept a larger box? This decides whether the 472 × 157 preset is a legitimate route or a dead end.
  3. For IBPS, which figure is real — 4.5 × 3.5 cm or 200 × 230 px? They contradict each other, and the notes carry no date.
  4. Does the declaration preset need the name filled in by hand before scanning, or does the portal expect the blank line? The tool shows the text verbatim from the PDF, including the blank.

Summary

Gemini's plan was not stupid and its research instinct was right. But it produced prose where code was needed, treated pixel dimensions as a free variable, and announced success without checking anything. Those three faults explain every bad result you saw, and none of them is fixed by writing a better prompt.

What fixes them is small and boring: one requirement at a time, recorded as data with its source and its unknowns; an algorithm that treats dimensions as fixed and size as a window; and a rule that the tool never claims success for a file it has not verified.

The corrected tool is a working example, with tests, so the pattern is available to copy rather than to reinterpret. All nine suites pass, and ten deliberate defects are caught — including two that only measurement can find. That last part matters more than the green ticks: a chain that cannot fail is not evidence, and this one now demonstrably can.

It also runs the way you asked: one 66 KB file, no server, on a phone or a laptop. Deep links mean a video description can open the exact tool with the exact requirement already selected.

Your instinct that the result was bad was correct, and your instinct that specific functions need real algorithms was correct. The review then went one step further than you asked: the research turned up a requirement that is internally inconsistent, and the honest answer for that requirement is not a better algorithm. It is a measurement, a warning, and a second documented option.

The next step is not more planning. It is one verified requirement, one proven tool, and one video — and the single most useful thing you can do today is spend twenty minutes on the live portal watching whether a 9 KB signature is rejected.
